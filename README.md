# TimeTrack · 时间管理

一个轻量的安卓时间记录应用：**随时新建任务、点一下就开始计时、停止即结束**，按天用饼图和条形图看时间去向，数据可导出成 CSV / JSON。

参考了番茄 Todo 和 ATracker 的交互思路，但刻意只做"正计时记录"这一件事——不含番茄钟。

---

## 功能

**计时页**
- 输入文字 → 点"开始"或按回车，**立刻开始计时**，没有多余步骤
- 大号计时器显示当前任务的已用时长，一键停止
- "最近任务"列表点一下即可切换过去
- 开始新任务时会**自动结束上一个**，不会出现两段计时重叠
- **补记一段**：忘了计时的事后补上，可以改日期，**不会影响正在跑的计时**
- **管理任务**：重命名、归档、恢复。重命名为已有名字会把两个任务**合并**（历史记录都保留）
- **忘停提醒**：一段连续计时超过 8 小时后，卡片会问"还在做这件事吗"，可以「结束到现在」或「改成更早」

**待办页**
- 两个清单：**今天**和**本周**，顶部一键切换
- 日待办每天早上都是空的（昨天的不自动延续，但可以左右翻回去看）
- 日待办页下方常驻显示**本周还没完成的事项**，可以直接在那里打勾——一件周任务今天做完了，勾掉即**整周完成**
- 未完成在前，已完成收在下面的「已完成」分组里，不占地方
- 打勾完成 / 再点取消，左滑删除，长按重命名
- 日期可左右翻，也可以点日历图标**直接跳到某一天**（月历以**周一为第一列**）
- 本周视图可点图标打开**周列表**，直接跳到某一周
- 日历与周列表上带红点的，表示那天 / 那周**还有未完成的待办**

**统计页**
- **可切换 日 / 周 / 月**三种粒度，默认今天
- **周和月与「上一期」并排对比**：每个任务显示本期、上期和增减，所以它回答的是"我这周比上周好点了吗"
- 可左右切换到任意历史期，但**不会翻到未来**（未来没有记录）
- 当日总时长 + 任务项数
- **环形饼图 + 比例条**：日 / 周 / 月**三种粒度都有**。环形给"这一段是怎么分的"一眼观感，
  条形给每一项的准确时长和占比
- **点饼图的扇区会弹出明细**：任务名、时长、占比；单日视图里还能直接跳到那一段去修改
- **条形图**：每项任务的时长、百分比，按耗时从多到少排列
- 正在计时的任务会**实时增长**，不需要手动刷新
- **点某一项就能修改或删除它这一天的时间段**——记错了、忘了按停止，都能修

**备份页**
- 范围：今天 / 最近 7 天 / 最近 30 天 / 全部
- **CSV**：每段计时一行（任务名、开始、结束、秒数、小时数、状态）。已带 UTF-8 BOM，Excel / WPS 双击直接打开，中文不乱码
- **JSON**：完整备份，保留原始时间戳；**待办列表始终全量导出**（导出范围只作用于计时记录）
- 保存位置由系统文件选择器决定，**应用不申请任何存储权限**
- 叫「备份」而不是「导出」，因为重点是**别丢数据**，而不是产出一个文件

**其它**
- 通知栏常驻显示正在计时的任务和已用时长，**并带一个「停止计时」按钮**（一步停止）
- **长按桌面图标**可以直接开始最近用过的任务（把"解锁→找图标→打开→输入→开始"5 步压到 2 步）
- **界面配色跟随壁纸**（Android 12+ 的 Material You），旧系统回落到内置配色
- **触觉反馈**：开始 / 停止 / 打勾 / 切换任务 / 删除时有一次短振动确认
- **界面是中性灰阶**：颜色只属于任务本身和删除操作，不再有大面积浅色容器
- 环形图在切换期次时扫入，而不是硬跳
- **使用说明**收在计时页的 ⓘ 里，不再散落在各个页面底部占地方
- 支持深色模式
- 适配 Android 8.0 ~ 15（minSdk 26 / targetSdk 34）
- **零后台唤醒**：没有闹钟、没有定时轮询，通知靠系统 chronometer 走秒

## 构建

环境已经在这台机器上准备好了（`.toolchain` 目录里），直接运行：

```powershell
cd TimeTrack
.\build.ps1                      # release 正式版（约 1.36 MB）
.\build.ps1 -Variant debug       # debug 版（约 9.4 MB，不混淆，排查问题用）
```

> 如果报"无法加载文件 build.ps1，未对文件进行数字签名"，是 PowerShell 执行策略的问题，
> 与项目无关。绕过方式：
> `powershell -ExecutionPolicy Bypass -File .\build.ps1`
> 或者按下面「手动构建」直接调 Gradle。

产物：

```
TimeTrack\app\build\outputs\apk\release\app-release.apk    1.36 MB
TimeTrack\app\build\outputs\apk\debug\app-debug.apk        9.47 MB
```

> **两个版本的包名不同**（release 是 `com.timetrack.app`，debug 是 `com.timetrack.app.debug`），
> 所以可以同时装在一台手机上，数据互相独立。日常用 release，出问题用 debug 对照。

### 工程自带 wrapper

`gradlew.bat` 已经生成好，`distributionUrl` 指向华为云镜像（官方 `services.gradle.org`
在该网络下**无法连接**，实测超时）。换机器时直接 `.\gradlew.bat assembleRelease` 即可。

### 手动构建（等价于脚本）

```powershell
$env:JAVA_HOME       = 'D:\Dev\JDK\jdk-21'
$env:ANDROID_HOME    = '..\.toolchain\android-sdk'
$env:GRADLE_USER_HOME= '..\.toolchain\gradle-home'

..\.toolchain\gradle-8.9\bin\gradle.bat assembleRelease
```

> `local.properties` 里的 `sdk.dir` 用 **Unicode 转义** 写中文路径，因为 `java.util.Properties` 按 ISO-8859-1 解码。移动 SDK 后需要按同样方式重写。

## 测试

`app/src/test/` 下有 **72 个纯 JVM 单元测试**，覆盖最容易出错的日期、统计与导出规则：

```powershell
cd TimeTrack
.\gradlew.bat :app:testDebugUnitTest
```

> ⚠️ 旧版本这里写过"本机沙箱禁止命名管道，Gradle 的 test worker 起不来，只能手工拼
> classpath 跑 JUnit"。**那条说明已作废**：现在 `testDebugUnitTest` 能直接跑
> （实测 47 个用例全绿，报告在 `app/build/reports/tests/`）。

四组测试：

| 测试类 | 用例 | 覆盖内容 |
|---|---|---|
| `TodoPeriodTest` | 16 | 周期键、ISO 周年边界、周历网格 |
| `StatsCalculatorTest` | 15 | 跨天切分、进行中区间、时钟回拨、窗口裁剪、合并排序、两期对比 |
| `SessionTimesTest` | 12 | 跨午夜规则、夏令时 23 / 25 小时日、忘停边界 |
| `ExporterTest` | 19 | CSV 的 BOM 与转义、小数点的语言无关性、JSON 的 null 与待办段 |
| `StatsPeriodTest` | 7 | 日/周/月窗口相邻不重叠、跨月步进不漂移、与待办周期规则一致 |
| `MigrationsSchemaTest` | 3 | 手写迁移与 Room 生成的 schema 是否一致 |

四个专门钉死的坑：

- **ISO 周年 ≠ 日历年。** `2027-01-01` 的周键是 `2026-W53`，不是 `2027-W53`——它属于
  2026-12-28 那一周。天真的 `年-W周数` 会把**同一个 ISO 周劈成两个键**，一条周待办于是
  同时出现在两个"周"里。测试逐日校验 2020–2030 每天都能从键回环到该周周一（0 失败）。
- **夏令时日不是 24 小时。** 如果按"当天零点 + N 分钟"算，柏林 2026-03-29 的
  `01:30 → 03:30` 会算成 2 小时（实际 1 小时），那天只有 23 小时。实现改成把每个时刻按
  时区解析；基准值是用 JDK 实测出来的（`tools/DstCheck.java`），不靠推理。无夏令时的
  时区（如上海）全年 0 处差异，所以这个修复不改变国内用户看到的任何结果。
- **迁移必须与 schema 逐字符一致。** `MigrationsSchemaTest` 读 `app/schemas/` 里 Room
  导出的 JSON 比对迁移语句。改了实体却忘了改迁移，这个测试会红——否则用户升级后
  App 一打开就崩。
- **小数点在任意语言下都是 `.`**，否则 CSV 列会错位。

## 装到手机

**方式一：直接拷贝（最简单）**
1. 把 `app-debug.apk` 通过微信 / QQ / 数据线传到手机
2. 手机上点开安装，若提示"未知来源"就允许一次

**方式二：数据线直连（调试方便）**
1. 手机「设置 → 关于手机」连点**版本号** 7 次，开启开发者模式
2. 「设置 → 开发者选项」里打开 **USB 调试**
3. 数据线连电脑，手机上弹窗点"允许"
4. 然后：

```powershell
..\.toolchain\android-sdk\platform-tools\adb.exe install -r app\build\outputs\apk\debug\app-debug.apk
```

> 首次打开会请求"通知"权限，同意后通知栏才会显示正在计时的任务。**拒绝也不影响计时功能**。

## 几个关键设计（改动前建议先读）

**1. 时长永远由时间戳推导，不在内存里累加**

数据库只存 `startTime` 和 `endTime`。显示时长用 `now - startTime` 实时算。这样进程被杀、手机重启、切到后台，计时都不会错乱。

**2. 全局只有一个"进行中"的计时段**

`endTime IS NULL` 的行最多一条。开始任何任务都在**同一个事务里**先关掉旧的再开新的，中途崩溃也不会留下两段重叠记录。

**3. 跨天的计时段按重叠切分**

`23:30 → 00:30` 这半小时会**分别计入两天各 30 分钟**，而不是粗暴地全算给开始那天。查询用的是"时间区间有重叠"而不是"开始时间落在当天"。

**4. 任务不做物理删除**

统计通过 `taskId` 关联任务。删任务只置 `archived = true`，历史统计因此不会出现"未知任务"。

**5. 通知栏不用定时刷新**

用系统的 chronometer（`setWhen` + `setUsesChronometer`）让系统自己走秒，所以运行时**零唤醒、零耗电**，服务也不需要常驻刷新循环。

**6. 两个图表都是手写的**

环形图是 `Canvas.drawArc` 写的（约 20 行），条形图用 Compose 布局实现（每个任务一条轨道加
一条填充），都不依赖任何图表库——省掉依赖让 APK 更小、构建更可控。

**7. 待办只存"完成时刻"，不存"已完成"标志**

`todos` 表里没有 `done` 字段，只有 `doneAt`。日／周两个清单共用这一张表，靠
`periodKey` 的格式区分（`2026-10-05` / `2026-W53`）。这带来一个意外的好处：

> 因为完成状态只有一个时间戳，**过去某一天的"本周还剩什么"可以纯推导重建**——
> `doneAt IS NULL OR doneAt >= 那一天开始`。翻回上周三，看到的就是上周三**当时**的样子，
> 不需要快照表，也不需要任何定时任务。

**8. 周期键必须用 ISO 周年，不能用日历年**

`TodoPeriod.weekKey` 取的是 `IsoFields.WEEK_BASED_YEAR`。这两者每逢跨年就不一致：
`2027-01-01` 属于 `2026-W53`（2026 有 53 个 ISO 周）。如果按 `年-W周数` 生成键，
**同一个 ISO 周会得到两个键**，一条周待办同时出现在两个"周"里，勾掉一个另一个还在。
`TodoPeriodTest` 逐日校验 2020–2030 的键能回环到该周周一。

**9. 有史以来的第一次数据库迁移是手写的**

v1 时期 `exportSchema` 是关的，所以没有 v1 schema 给 `@AutoMigration` 做对比，v2 只能手写
`MIGRATION_1_2`。为了让它可验证，`app/schemas/` 里的 `1.json` 是在改实体**之前**导出的，
`2.json` 是改完之后导出的，`MigrationsSchemaTest` 拿两者比对迁移语句。

Room 会在升级后第一次打开数据库时按 `2.json` 重新校验，**任何列类型、可空性或索引名的差异
都会抛异常**——用户看到的就是"更新后 App 一打开就崩"。

**10. 时间编辑器的锚点是"这一段自己的日期"，不是"正在看的那一天"**

一段跨午夜的记录会同时出现在两天的统计里。如果编辑器拿"正在查看的那天"当锚点，
用户只是打开又保存，这一段就会被整体挪走一天——一个不报错、只是悄悄改错数据的 bug。
所以锚点取 `startTime` 所在的日期，并且这个日期在编辑器里可以改（"记到别的天去了"
和"时间记错了"是同一类错误）。

`SessionTimesTest` 里那条 `stored millis read back as the times that produced them`
就是钉住"读出来原样存回去必须是空操作"。

**11. 提醒不靠定时器，靠读状态**

"忘停提醒"如果用 `AlarmManager` 的精确闹钟来做，会打破 `TimerService` 那条"零唤醒"的设计，
而且 Android 12+ 需要用户去系统设置里手动授予 `SCHEDULE_EXACT_ALARM`。所以它是**读状态**
而不是**定闹钟**：App 在前台时观察正在进行的区间，超过 8 小时就显示卡片。

代价是诚实的：**一天不打开 App 就看不到这个提醒**。但通知栏那条常驻通知本身就是提醒，
真正看不见的时间窗口很小。

**12. 桌面快捷方式是"发布请求"，不是"直接调用"**

长按图标的快捷方式复用的是同一个 Activity，而且 App 已在前台时只会触发 `onNewIntent`
（不会创建新的 composition）。所以 Activity 不直接碰仓库——它把 taskId **发布**到
`StartRequest`，由 Compose 层观察并消费一次。这样 Activity 保持对业务无知，也天然避免了
重复开始计时。

**13. 统计的三种粒度共用同一套窗口规则**

`StatsPeriod.bounds` 返回的是**半开区间** `[start, untilExclusive)`。这样"上一期"和"本期"
恰好首尾相接，既不重叠也不留缝——否则跨月的那一天会被算两次或被漏掉。
`StatsPeriodTest` 用"上期的结束必须等于本期的开始"这一条把三种粒度一起钉住。

**14. 界面配色和任务配色是两套完全不相干的东西**

- **界面**是中性灰阶，而且**固定**：不跟随壁纸（Material You 试过一版，已关闭——它会给界面
  注入一个来自壁纸的色相，而任务色才是这里唯一有含义的颜色）
- **任务色**来自 `TimeTrackRepository.colorFor(name)`，是按任务名哈希的固定调色板，因为同一个
  颜色要同时出现在图表、通知和导出的 JSON 里，必须长期稳定

主题文件里原本有一条注释写着"为了任务颜色稳定，所以不能开动态取色"。**那是错的**——两套调色板
根本没有交集。这次把注释改对了，也把动态取色关掉了，两个决定是分开的。

**顺手踩了一个坑，值得记下来：只覆盖一半颜色角色，等于没覆盖。**

`lightColorScheme(...)` 里**没写**的角色会回落到 Material3 的**基线配色，而基线是紫色的**。
这些角色并不冷门：

| 角色 | 谁在用 | 漏掉的后果 |
|---|---|---|
| `inverseSurface` | **每一次 Snackbar** | 弹出一条紫色的提示条 |
| `secondaryContainer` | 分段控件选中的那块、FilterChip | 紫色的选中块 |
| `surfaceTint` | 所有 Card | 卡片被叠一层色，看起来发脏 |

所以"中性灰阶"当时根本没生效，实际是**灰底 + 随机冒出来的紫色块**——看起来像坏了，而不是
像设计过。现在这些角色全部显式赋值；`surfaceTint` 设为透明，`surfaceContainer*` 全部等于
`surface`（对话框和菜单是白色浮层），而灰色填充 `surfaceVariant` 只留给一个东西：正在计时。

**15. 环形图删掉又装回来了**

我一度以"和条形图重复"为理由把它删了，**这个判断是错的**。两张图回答的是不同问题：

- **环形**给你"这一天是怎么分的"——一眼的比例感
- **条形**给你"每一项到底多少、占多少"——准确的数字

下面那张条形图确实在充当环形的图例，但**"图例"不等于"替代品"**：比例感和精确值是两种不同的
信息，不是同一份信息的两种画法。

留个记录：删的时候我写得很有把握，实际用起来是错的。**没有真机验证的设计推理，就只是推理。**

**16. 底部导航的四个图标是自绘的**

`material-icons-core` 里没有下载图标，而往一排线性图标里塞一个实心图标，正是让界面看起来
"拼装的"而不是"设计的"那种不一致。四个矢量加起来几 KB，共用一套规格（24dp 网格、1.75dp
描边、圆头端点）。这和手写图表是同一个判断：**风格统一和体积可控比省事重要**。

**17. 唯一不可逆的操作才配弹确认框**

时间段列表里的删除是全局唯一"点了就没、也没有撤销"的操作，所以它走确认框，并在框里说清
"这一天的统计会同步减少"。反过来说，界面上原本那些解释性文字——"删除是彻底的""重命名为
已有任务名会合并"——都被删掉了：前者该出现在确认框里，后者已经有 `已合并到「X」` 这样的
即时反馈，提前用一段话解释只是在抢答用户马上就会看到的提示。

**18. 卡片预算：填充只表示状态**

改造前四个页面加起来有 14 张卡片，每个模块都被装进一个浅色圆角容器里。问题是**当每样东西
都是卡片，卡片就不再表示"这是一个独立对象"，而只是"这里有一块圆角背景"**——层级因此消失，
用户的视线没有落脚点。

| 页面 | 之前 | 现在 |
|---|---|---|
| 计时 | 4 张 | **1 张**（正在计时） |
| 待办 | 3 张 | **2 张**（今天的清单、本周） |
| 统计 | 5 张 | **0 张** |
| 备份 | 2 张 | 2 张（还没合并，见"以后想扩展"） |

规则有两条：

- **填充 = 状态，不是分组。** 全 App 只有"正在计时"这一个状态用填充背景，于是那块灰色重新
  有了含义：它一亮，就说明有东西在跑。"进行中"也从整行填充改成行首一条 3dp 竖条——
  同样的信息，说的是而不是喊的。
- **描边卡片 = 一个可以整体操作的对象。** 待办页最终回到两张卡，因为"一份清单"确实是一个
  对象；输入行放进卡片里当第一行，而不是漂在卡片外面。

我第一次把待办页砍到零卡片是**砍过头了**：页面变成一根没有落点的长柱子。层级确实该由
`titleSmall` 小标题、32dp 的块间距和分隔线建立——**间距的对比本身就是分组**，全局统一 16dp
恰恰是让分组消失的原因——但"克制"和"什么都没有"是两回事。

**19. 饼图的点击命中是纯几何，而且有测试**

`sliceIndexAt` 只收浮点数、不碰任何 Compose 类型，所以边界用例能用普通单测覆盖：正上方那一刀
归谁、中间的洞不属于任何扇区、环外不算、只有 1° 的极小扇区也要能点到。共 9 条。

触摸命中就是这么一类代码——**它只会在某一个边界上错，而隔着触摸屏调试这件事极其痛苦**。写成
纯函数是让它可测的唯一办法。

另外命中用的是**完整的扇区角度，不是动画中的角度**：环形正在扫入时点一下，落在还没画出来的
扇区上也算数。动画是装饰，不该让控件变得难以点中。

**20. 左滑删除的背景层，必须被不透明的行盖住**

`SwipeToDismissBox` 的 `backgroundContent`——那层粉红底加垃圾桶——**永远绘在内容之下**，它靠
内容把自己遮住。而待办行的 `Surface` 我当时给了 `color = Color.Transparent`，于是粉红底和
垃圾桶**在静止状态下就一直露着**，每一行看起来都像一张丑陋的粉色卡片。

这个 bug 从阶段 1 就存在，我带着它发了 5 个版本。这个页面你说过两次"不好看"，我两次都归因到
别处（第一次归到主题角色泄漏——那也确实是另一个真 bug），直到你把截图发过来，**一眼就看见了**。

教训很直接：**"我看不到界面"不是继续猜的理由，而是要截图的理由。** 在没有画面的情况下做了
三轮视觉推理，正确的做法是**第一轮就要截图**。

## 数据存在哪

应用私有目录下的 SQLite 数据库（**当前版本 v2**）：

```
/data/data/com.timetrack.app/databases/timetrack.db
```

表：`tasks`、`sessions`（计时域）、`todos`（待办域）。

卸载应用会一并删除，**所以重要数据请定期用导出页备份**。从 v1 升到 v2 会走
`MIGRATION_1_2`，只新建 `todos` 表及其索引，**既有计时数据原样保留**。

## 以后想扩展

- **年统计 / 自定义区间**：`StatsPeriod` 已把窗口规则抽成纯函数，加一种 `StatsMode` 即可；`rangeStat` 接受任意区间
- **番茄钟**：在 `Session` 上加 `plannedMillis` 字段，`TimerService` 里用 `setChronometerCountDown(true)`
- **自动备份**：把 `Exporter` 的输出定期写入 SAF 目录
- **真正的后台忘停提醒**：需要 `WorkManager` 或非精确闹钟，代价是多一次唤醒和一个依赖；
  现在的前台检查已经覆盖大部分场景
- **待办的习惯型重复**：现在的模型是"一次性待办"。习惯型（每天／每周自动出现、不用重新输入）
  需要再加一张完成记录表，`Todo` 本身不用动
- **把周待办拉到某一天做**：`todos` 表已有 `periodKey`，加一条"本期激活"的记录即可，不用改表结构
- **应用级大标题栏（LargeTopAppBar）**：现在每个页面自己带标题，加一个应用级大标题会和底部导航
  的标签重复，而且需要把每页的滚动状态提升到 `AppRoot` 再接 `nestedScroll`。收益不明，暂缓
- **备份页的两张卡片合并成一张**：范围和格式是同一个决策，应该在一个容器里。这次没做
- **大字体 / 高对比度实测**：结构上不会有问题，但需要真机把系统字号调到最大确认一遍
